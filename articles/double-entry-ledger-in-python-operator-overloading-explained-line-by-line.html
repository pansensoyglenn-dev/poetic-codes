01 — The Idea

What Is a Double-Entry Ledger?

📒 Every Entry Has Two Sides

Accounting's golden rule: every transaction affects at least two accounts. If you receive cash, you also record where it came from. Debits and credits must balance to zero — always. If they don't, something is wrong with your books.

In this project, a Debit is a positive amount and a Credit is the exact same amount, negated. Because __add__ and __neg__ are implemented, adding an entry to its opposite produces exactly zero. A ledger is balanced when sum(entries) == 0.

This is polymorphism through operator overloading: the call site sum(entries) doesn't know or care whether it's holding Debits, Credits, or both. It just calls +, and each object answers with its own arithmetic.

The Shape of the Data

A Debit holds a positive amount. A Credit is a Debit that has been negated — literally produced by -debit. Both are entries. Both know how to add, compare and hash themselves. A transaction holds two entries and a description.

Note on the design: a Credit is just a Debit with a negative amount. This keeps the ledger simple — we don't need two classes to get two behaviors. The operator does the differentiation.

📜 Accounting in five minutes

You do not need a business background for this page, only five ideas. Double-entry bookkeeping was described in print by Luca Pacioli in 1494 (although merchants used it earlier), and it has survived five centuries because it makes mistakes detectable: every event is written down twice, from two points of view, and the two must agree.

  1. Accounts are labelled buckets of money: Cash, Supplies, Sales Revenue.
  2. A transaction is one business event. It always touches at least two accounts.
  3. A debit is an entry on the left side of an account; a credit is an entry on the right. The words are bookkeeping labels, not “good” and “bad”.
  4. The golden rule: for every transaction, total debits equal total credits.
  5. The ledger is the collection of all accounts. If the golden rule held for every transaction, the whole ledger balances.

Total of the debit balances: 1,374.50 + 75.50 = 1,450.00. Total of the credit balances: 250.00 + 1,200.00 = 1,450.00. Equal — this check is called a trial balance. The program below does the same arithmetic with nothing but a dictionary and a loop.

Modelling choice you should notice: this project stores one signed number: debit = positive, credit = negative. That is why Sales Revenue shows −250.00 in the code even though revenue is good news — a report would flip the sign based on the account type. Real systems often store separate debit and credit columns or integer cents; signed amounts are simply the neatest fit for operator overloading.

Balanced does not mean correct. An invariant that total debits equal total credits catches one-sided entries and arithmetic slips. It does not catch posting 250 to the wrong account on both sides, or forgetting a whole transaction. Treat sum == 0 as a smoke alarm, not a guarantee.

A precision note about sum(entries) == 0. The page’s headline expression is the idea: the total of all signed entries is zero. In the code, the ledger-wide total adds the entry amounts (Decimal numbers), because Debit.__add__ deliberately refuses to combine different accounts. The + operator does its real work within one account — see account_balance() — and the Bug Hunt below explains why.

🐞 Bug hunt: the __start__ seed

The first draft of this page computed the balance with sum(self._entries, start=Debit("__start__", Decimal("0"))) and explained that a neutral “start” account was needed because entries on different accounts cannot be added. Unfortunately the idea fails: that code raises ValueError: Cannot add __start__ to Cash on the very first addition, and no seed would fix it, because the second step then tries to add two different real accounts. The program below reproduces both failures and shows the fix. Detective work like this — read the error, find the first failing step — is a core debugging skill.

What the fix teaches: an operator you define has rules (same account only), and every function that uses it — including built-ins like sum — must respect them. When a rule does not fit a task (summing across accounts), change the data you feed in (use the amounts), not the rule.

📋 Summary: the design in fourteen sentences

  1. @dataclass(frozen=True) — makes Debit immutable. Once an entry is recorded, it can't be changed. That is exactly what a ledger needs.
  2. account: str, amount: Decimal — the two fields. Decimal is used instead of float because money arithmetic must be exact.
  3. __add__ — first checks type: return NotImplemented if other isn't a Debit. Then checks the account: adding to a different account raises ValueError. Finally returns a new Debit.
  4. __neg__ — returns a new Debit with the amount negated. This is what turns a debit into a credit.
  5. __eq__ — compares (account, amount) tuples. Returns NotImplemented for non-Debit types, so Python can fall back to "not equal".
  6. __hash__ — hashes the same (account, amount) tuple that __eq__ compares. (A frozen dataclass would generate a matching pair by itself; writing both by hand shows the rule that equal objects must hash equally.)
  7. __repr__ — shows the class name and fields. Makes debug output readable.
  8. Credit = Debit — a credit is just a debit alias. The actual differentiation happens through the sign, which __neg__ controls.
  9. Transaction — a plain dataclass holding description, two account names, and an amount.
  10. Transaction.entries() — produces the pair: a debit for the debit_account and a credit (negated debit) for the credit_account. The same amount, opposite signs.
  11. Ledger.post() — appends the transaction and extends the entry list with the two entries.
  12. Ledger.balance() — sum((e.amount for e in self._entries), start=Decimal("0")). We add the amounts because Debit.__add__ refuses to combine different accounts, so a ledger-wide sum of Debit objects is impossible. The first draft used a __start__ seed instead and crashed; see the Bug Hunt above.
  13. Ledger.is_balanced() — self.balance() == 0. That's it. The check is a single comparison.
  14. account_balance() — collects one account's entries and adds them with the + operator, seeded with a zero entry for the same account. This is where operator overloading does real work.
  15. total_debits() and total_credits() — split the entries by sign. These should be equal in a balanced ledger.

⚠️ Common mistakes

Raising TypeError inside __add__. Return NotImplemented. Let Python build the TypeError itself.

Using float for money. 0.1 + 0.2 is not 0.3. Use Decimal.

Forgetting @dataclass(frozen=True). Then a debit can be mutated after being recorded, and your ledger becomes unreliable.

Mismatched __eq__ and __hash__. Two equal entries must hash the same. Keep them consistent.

Mixing currencies in one ledger. Add a currency field to Debit and check it in __add__, or raise on mismatch. (See the Currency Converter for the full pattern.)

05 — Dunder Methods

The Operators Behind the Ledger

Each dunder method hooks a Python operator into the Debit class. Here's how each one is used in the ledger.

➕ __add__

Hooks a + b. Adds two debits on the same account. Refuses cross-account addition.

Debit("Cash", 10) + Debit("Cash", 5)
# → Debit("Cash", 15)

Debit("Cash", 10) + Debit("AR", 5)
# → ValueError

➖ __neg__

Hooks -a. Returns a new Debit with the negated amount. This is how a credit is created.

-Debit("Sales", 250)
# → Debit("Sales", -250)
#    (a credit)

🟰 __eq__

Hooks a == b. Compares both the account and the amount.

Debit("Cash", 10) == Debit("Cash", 10)
# → True

Debit("Cash", 10) == Debit("Cash", 11)
# → False

🔒 __hash__

Enables entries in sets and as dict keys. Must be consistent with __eq__.

{Debit("Cash", 10),
 Debit("Cash", 10)}
# → {Debit("Cash", 10)}
#    (one entry, deduplicated)

⚙️ Design rules that keep operators trustworthy

  • Return new objects. a + b must not modify a or b. With frozen=True Python enforces this for you.
  • Return NotImplemented for types you do not understand, and never raise TypeError yourself (Mistake 1).
  • Keep __eq__ and __hash__ in agreement. Equal objects must hash equally (Mistake 4).
  • Make operators total or explicit. Either an operator works for every pair of values of the supported types, or it raises a clear, specific error (ValueError for different accounts).
  • Do not be clever. An operator should mean what a reader expects. + that adds money is great; + that posts to a database is a trap.
06 — The Payoff

Why sum(entries) == 0 Always Holds

The Proof

It comes down to one algebraic identity. For every transaction t with amount a:

entries(t) = (Debit(debit_account, a), Debit(credit_account, -a))

Sum of entries across all transactions:

Σ entries = Σ (a) + Σ (-a)
          = Σ (a - a)
          = Σ (0)
          = 0

It's true by construction. Every transaction adds one positive and one negative of the same amount. The ledger's balance is zero before you even look at the number — the invariant is baked into how the data is created.

🚧 What the invariant can and cannot promise

Kind of errorCaught by sum == 0?Why
A one-sided entry (only a debit was recorded)✓ YesThe lonely amount has no partner.
A typo on one side (250 vs 205)✓ YesThe two sides differ.
The same typo on both sides✗ NoBoth sides still match.
Posting to the wrong account on both sides✗ NoThe totals are unaffected.
A forgotten transaction✗ NoNothing is unbalanced, merely missing.
A transaction posted twice (as a whole)✗ NoBoth copies balance.

This is why real accounting also uses reconciliations, audit trails and review. The invariant makes one whole class of bugs impossible; it does not make the books right.

11 — The Road Ahead

Wrapping Up

🏁 What You've Learned

You met operator overloading in a real domain: a double-entry ledger where every entry is a Debit and every credit is a Debit negated. Because __add__ and __neg__ are implemented, a single expression balances the books — no helper methods, no special counters.

The same technique scales: add a currency field and the pattern becomes a full accounting system. Add __lt__ and you can sort entries by amount. Add __hash__ and entries become set- and dict-friendly.

Key Takeaways

  • Operator overloading is polymorphism. sum(entries) doesn't know or care what class it's holding — it just calls +.
  • __neg__ is the whole trick. A credit is literally a debit negated. The same amount appears with opposite signs, so the total is zero.
  • Return NotImplemented, don't raise. Let Python decide whether an operation is valid across the types involved.
  • Keep __eq__ and __hash__ consistent. Two equal entries must hash the same, or sets and dicts misbehave.
  • Use Decimal for money. Float arithmetic loses cents. Decimal keeps the books exact.
  • Balanced is not the same as correct. The invariant catches one-sided entries and slips, not wrong-account or missing transactions.
  • Read the first failing step. The __start__ bug was found by asking which addition raised first, not by guessing.
  • Operators have rules; honour them everywhere. Built-ins such as sum obey your __add__, including its same-account rule.
  • Invariants are stronger than checks. sum(entries) == 0 is true by construction, not by a runtime assertion — the data structure can't produce a wrong answer.

🙋 Frequently asked questions

Why is Credit = Debit not a subclass?

A subclass would let isinstance(x, Credit) work, but it would also let a Credit carry a positive amount, breaking the rule that credits are negative. A single class with a sign cannot be in an inconsistent state. The cost is that you test entry.amount < 0 instead of the type.

Why does Debit define __eq__ and __hash__ when a frozen dataclass would generate them?

For teaching: writing them by hand shows the rule that equality and hashing must agree. In production code you would normally delete both and rely on @dataclass(frozen=True), which generates a consistent pair (the test program does exactly that).

Should a real ledger store a signed amount?

Some do, some store separate debit and credit columns, and many store integer minor units (cents). The best choice depends on reporting needs. Signed amounts make the arithmetic beautifully simple, which is why they suit this lesson; a presentation layer decides how to display them.

Can I use float if I round at the end?

You can, and many programs do, but errors can accumulate and equality checks like balance == 0 become unreliable. Decimal or integer cents let you keep the exact check that makes this design elegant.

Why does sum(entries) fail without start=?

sum begins at the integer 0, so its first step is 0 + entry. int does not know about Debit, and Debit has no __radd__, so Python raises TypeError. Supplying start= with a matching object, or summing numbers, avoids it.

Is operator overloading “too magical”?

It is a tool with a cost: readers must know what + does for your type. It pays off when the operator matches a real mathematical meaning (adding money, negating a debit). Avoid it when a named method like post() would be clearer.

📚 Glossary

Account

A named bucket of money, such as Cash.

Debit / Credit

The two sides of an entry. Here: positive and negative amounts.

Journal entry

One recorded transaction with a debit side and a credit side.

Ledger

The complete set of accounts and entries.

Trial balance

A list of all account balances whose total must be zero.

T-account

A drawing with debits on the left and credits on the right.

Invariant

A condition that must always hold, here: total of entries = 0.

Dunder method

A method with double underscores that Python calls for operators and built-ins.

Operator overloading

Giving your class its own meaning for an operator such as +.

NotImplemented

A return value meaning “I cannot handle this pair of types.”

Reflected method

The right-hand operand’s method (__radd__) tried after the left one declines.

Dataclass

A class whose boilerplate methods are generated from its fields.

Frozen

Read-only after creation.

Decimal

Exact decimal arithmetic for money.

Seed (start)

The initial value for sum().

Hash

A number used by sets and dicts to find equal objects quickly.
